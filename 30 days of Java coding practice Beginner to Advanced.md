Daily Question Structure

Every day must contain exactly 5 questions, with one question from each category below:

Mixed Real-World Scenario: A practical problem based on situations such as banking, shopping, ticket booking, student management, billing, inventory, food ordering, ATM operations, or other real-life systems.
Interview-Based Coding Question: A Java programming question commonly associated with entry-level technical interviews, covering problem-solving, logic, and fundamental data structures.
Company-Style Programming Problem: An original coding challenge inspired by the style of entry-level technical assessments used by software companies. Do not falsely claim that a question was asked by a specific company.
Predict the Output: Provide a Java code snippet and ask me to determine the exact output. Include questions about variables, operators, conditions, loops, strings, arrays, methods, and object-oriented concepts as my skills progress.
Debug the Code: Provide a Java program containing one or more intentional bugs. Ask me to identify the errors and correct the program.

Rotate the topics and contexts so that the questions remain interesting and do not repeat the same logic unnecessarily.

Difficulty and Quality Rules
Provide exactly 5 questions per day and exactly 150 questions overall.
Every day must contain all five question categories in the specified order.
Use Java throughout. Make all code snippets compatible with a clearly stated Java version, preferably Java 17.
Explain unfamiliar problem terminology briefly without revealing the solution.
Include meaningful edge cases, such as zero, negative numbers where relevant, empty strings, duplicate values, and boundary conditions.
Keep the initial questions simple and increase the difficulty progressively.
Avoid repeating identical problems with only different numbers or names.
Make the problems solvable using the concepts taught by that day.
Ensure the sample outputs are correct and consistent with the problem statements.
For debugging questions, make the intended behavior clear and ensure the bugs are deliberate and identifiable.
For output-prediction questions, use deterministic code without ambiguous behavior or environment-dependent results.
Do not include solutions, hints that reveal the approach, answer keys, corrected debugging code, or explanations of the output anywhere in the practice workbook.
Do not reveal answers in a final answer section or append an answer key.
Use original questions or standard practice concepts. Do not invent company attribution.
Make the document easy to navigate, with a table of contents for Days 1–30 and clear headings.
Keep the workbook practical and focused on writing code, tracing execution, and debugging rather than memorizing theory.
